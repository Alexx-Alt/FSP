# FSP / ИТ-MATCH PRO v6

Версия объединяет визуальный язык `fsp-match-nova-final-v5` с механиками `fsp-match-3.0-clean` и переносит их в стек репозитория: Laravel + Inertia + Vue 3 + TypeScript + MySQL 8.

## Основной цикл

`желаемый грейд → category assessment → подтверждённый грейд → evidence tree → explainable Match → invitation/clarify/perspective → interaction case → gap-задачи/комментарии/алерты → новое evidence → обновлённый Match`.

### Assessment

Кандидат выбирает желаемый грейд. Официальный `confirmed_grade` назначается только assessment по категории. Неподтверждённый грейд не скрывает человека, а понижает вес в Match. Для качества хранятся варианты теста и test-retest пары.

### Древо знаний

Навыки моделируются иерархически, например `Backend → Данные → PostgreSQL → Индексы / Транзакции / Оптимизация`. Каждый узел имеет evidence-state: `confirmed`, `partial`, `claimed`, `unknown`. Источники: assessment, practical task, FSP ID, external, self.

### FSP ID

FSP достижения не назначают грейд. Они подтверждают отдельные компетенции и дают небольшой bonus внутри уже релевантной категории/грейда. Отсутствие FSP-истории не делает кандидата невалидным.

### Explainable Match

`MatchEngine` учитывает категорию, подтверждённый грейд, покрытие стека, зарплатное пересечение, формат работы и небольшой evidence/FSP boost. Результат — не только процент, а маршрут: `invite`, `clarify`, `perspective`, `observe` плюс причины и gaps.

## Замечание руководителя: процесс, а не профиль

Hiring моделируется через `interaction_cases`. Один кандидат может иметь несколько ЛПР и длинную историю. У кейса есть владелец, участники, статус, прогресс, next action, priority, адресные задачи, комментарии, alerts и audit events. Для повторных входов есть `duplicate_group`, для возврата к старому контакту — `reopened_from_case_id`. Старый отказ или похожий повтор не является автоматическим основанием снова отклонять кандидата.

Контакты открываются только после взаимного шага; demo хранит это как `contacts_unlocked_at`.

## 3-срезная аналитика

1. **Люди / команда.** Кандидат сравнивает себя с peers; работодатель сравнивает сотрудников; администратор видит кандидатов системы.
2. **Компании.** Candidate/employer/admin видят benchmark работодателей: hiring quality, response time, acceptance rate, вакансии и зарплатный ориентир.
3. **География.** По городам России считаются кандидаты, вакансии, компании, доля подтверждённого грейда, ожидания/предложения по зарплате и `pressure = jobs / candidates`.

## Роли и доступ

`applicant`, `employer`, `admin`. Кандидат не видит внутренние комментарии работодателя. Работодатель видит процессы своей компании. Admin видит системный уровень.

## AI policy

LLM может помогать с объяснениями, кластеризацией комментариев и админскими подсказками, но обязательный путь работает без GPU. LLM не назначает грейд, не блокирует кандидата, не открывает контакты и не принимает финальное решение о найме.

## Валидация

Синтетический seed содержит закрываемые пары «вакансия ↔ кандидат», подтверждённые и неподтверждённые грейды, test-retest пары, FSP achievements, разные города, компании, переоткрытые и потенциально дублирующиеся hiring cases. Это позволяет вручную проверять Match и стабильность assessment.
